# WAT Codec Strictness Policy

This table records known Rust/WAT parity mismatches where the WAT codec
primitive is stricter, narrower, or scanner-level compared with the current Rust
implementation. The policy choice is explicit so WAT modules are not promoted to
drop-in replacements where compatibility behavior is still intentional.

Policy choices:

- `change Rust to stricter`: Rust should reject the input for canonical or
  proof-relevant paths.
- `add permissive WAT mode`: WAT should gain an explicit compatibility entry
  point that mirrors Rust behavior.
- `keep both with named policies`: expose strict/canonical and compatibility
  behavior as separate policies.
- `not replacement`: WAT is useful as a scanner/validator, but must not replace
  the Rust parser until missing semantics are implemented.

| Area | Observed mismatch | Current Rust behavior | Current WAT behavior | Recommendation | Security/proof implications | First tests to add |
| --- | --- | --- | --- | --- | --- | --- |
| Base64url noncanonical tail bits | Noncanonical unpadded base64url tails can decode to the same bytes as canonical encodings. The encoding parity runner records these as `b64.noncanonical.*` divergences: Rust accepts, WAT rejects. | `edgerun_encoding::base64::base64url_decode_into` accepts 2- and 3-byte tails without checking unused low bits. | `encoding-core.wat` `base64url_nopad_decode` rejects noncanonical tails. | `change Rust to stricter` for canonical decode APIs; keep a separately named compatibility helper only if a real caller needs legacy acceptance. | Accepting multiple encodings for the same bytes weakens content-addressed proofs, signed preimages, cache keys, and admission policy hashes if encoded text is part of the committed form. Strict canonical decode gives one text form per byte string. | Add Rust unit cases for 1-byte and 2-byte decoded tails where unused bits are nonzero, expecting error. Add parity cases proving canonical `Zg`/`Zm8` pass and noncanonical tail variants fail in both Rust and WAT. |
| PEM lowercase labels | Lowercase encapsulation labels such as `-----BEGIN certificate-----` differ. The DER/TLS parity runner marks `pem_lowercase_label` as `wat-stricter`. | `pem_rfc7468::decode_label` accepts the lowercase label and returns it. | `pem-rfc7468.wat` `pem_find_boundaries` rejects lowercase labels. | `keep both with named policies`. Use strict RFC7468-style labels for certificate, trust, and proof paths; allow a named compatibility importer for user-supplied legacy PEM if needed. | PEM labels identify object class before DER validation. Lowercase acceptance is usually compatibility-safe after DER validation, but it should not be allowed to create alternate textual forms in proof trails or policy-bound artifacts. | Add `pem_label_strict_rejects_lowercase` and `pem_label_compat_accepts_lowercase` tests if a compatibility API is kept. Add a proof-path test that canonical re-emission always uses uppercase labels. |
| TLS unknown content type | A TLS record with unknown content type, e.g. `0x13`, is accepted by Rust but rejected by WAT. The DER/TLS runner marks `tls_record_unknown_type` as `wat-stricter`. | `TlsRecord::from_bytes` parses the 5-byte header, length, and fragment without validating content type. | `tls-frame.wat` `tls_record_header_decode` accepts only known record content types. | `keep both with named policies`. Rust should keep a raw record parser if needed, but strict TLS record validation should be a separate named policy used before proof/economic decisions. | Unknown record types are acceptable for low-level capture tools, but not for admission, settlement, or certificate/TLS proof claims. A proof verifier must not sign or pay for a record whose semantic class is unknown. | Add `tls_record_raw_accepts_unknown_type` and `tls_record_strict_rejects_unknown_type`. Add parity case asserting WAT strict and Rust strict agree on `0x13 03 03 00 00`. |
| TLS future version records | A record with a future outer version, e.g. `0x0305`, is accepted by Rust but rejected by WAT. The DER/TLS runner marks `tls_record_bad_version` as `wat-stricter`. | `TlsRecord::from_bytes` does not constrain `version`. | `tls-frame.wat` rejects unsupported/future outer record versions. | `keep both with named policies`. Raw parsing may preserve bytes for diagnostics; strict validation should reject versions not admitted by the negotiated protocol policy. | Future-version tolerance is useful at byte-capture boundaries but dangerous in verifiers because it can make claims about protocol semantics not covered by the implementation. Strict policy prevents downgrade/upgrade ambiguity in signed records. | Add strict Rust tests for accepted outer versions and rejected `0x0305`. Add a raw parser test proving future versions can still be inspected without being admitted as valid TLS records. |
| Percent decode malformed escapes | Historical Rust compatibility preserved malformed escapes such as `%`, `%G`, or `%XX`; WAT rejects them. The deleted-oracle misc runner now records fixed WAT expectations instead of compiling the deleted Rust oracle. | Deleted local compatibility behavior preserved malformed `%` byte-by-byte. | `percent-url-form.wat` `percent_decode_strict` rejects malformed percent escapes. | `keep named policies`. Use strict decode for canonical URI, manifest, package, and proof paths. Reintroduce permissive decode only as an explicitly named legacy importer if a real caller needs it. | Malformed escape preservation creates alternate spellings and can hide boundary confusion between encoded and literal `%`. Proof paths need fail-closed decoding before hashing, policy matching, or capability routing. | Covered by `percent-url-form-smoke.js` malformed escape cases. Add compatibility tests only if a permissive legacy importer is intentionally restored. |
| Plus-as-space form behavior | `foo+bar` decodes differently depending on whether the input is generic percent-encoded text or `application/x-www-form-urlencoded`. The misc runner now keeps WAT fixed expectations and records the deleted Rust oracle separately. | Deleted local compatibility behavior treated `+` as space in form-like decode paths. | `percent_decode_strict` preserves literal `+`; the WAT form scanner returns raw spans and does not decode values. | `keep named policies`. Generic percent decode must preserve `+`; form decode must explicitly apply plus-as-space before strict percent decoding. | Collapsing generic percent and form semantics can change signed URLs, route keys, object names, OAuth values, and policy filters. Named policies prevent `+` from becoming an untracked alternate spelling for space. | Covered by `percent-url-form-smoke.js` generic `+` and form raw-span cases. Add form composition tests where caller policy maps `+` to space. |
| DNS compression pointers | Compressed names such as a `www` label followed by `0xc0 0x00` decode in Rust with an offset map, while WAT rejects compression pointers. The misc runner states WAT is not a DNS message-name replacement until pointer resolution is added. | `decode_domain_name` can resolve compression pointers when provided an offset map. | `dns-name.wat` scans only uncompressed wire names and rejects pointer labels. | `not replacement`. Use WAT only for uncompressed DNS name validation until it implements bounded pointer resolution and loop detection. | DNS message proofs must hash and verify the actual wire message. Rejecting pointers is safe but incomplete; accepting names without pointer semantics would fail common DNS packets. Pointer resolution must be bounded to prevent loops and offset confusion. | Add WAT/Rust parity cases for compressed suffix, pointer loop, pointer to middle of label, pointer out of bounds, and max indirection depth. Add strict DNS message tests that reject loops and accept a valid compressed query/answer name. |
| TOML malformed scalar fallback | Inputs like `0xzz` or an unterminated string are treated by Rust as strings but rejected by WAT. The misc runner flags this as a policy decision before replacement. | `from_toml_str` / `parse_toml_value_simple` fall back to `JsonValue::String` for unknown or malformed scalar-looking values. Full-document parsing also ignores non key/value non-table lines. | `toml-scan.wat` rejects malformed scalar scanner input and non key/value scanner lines. | `change Rust to stricter` for manifest, standards, and policy files. If legacy loose TOML is still needed, expose it as a separate compatibility parser. | Silent scalar fallback can turn invalid policy, manifest, or proof metadata into accepted strings. That weakens auditability because malformed numeric, boolean, or string fields may survive validation under the wrong type. | Add TOML parser tests rejecting `value = 0xzz`, `value = "unterminated`, and bare `missing` lines in strict mode. Add manifest/policy loader tests proving strict TOML is used for standards inputs. |
| HTTP/1 full parser permissiveness vs scanner strictness | HTTP/1 parity currently covers method, status, header, and transfer-token validators. The runner records a gap: full Rust message parsing is more permissive than the scanner WAT. | `HttpRequest::from_http` reconstructs relative targets, defaults missing Host to `localhost`, ignores malformed header lines without `:`, accepts any version prefix starting with `HTTP/`, and truncates body to available `Content-Length`. | `http1-scan.wat`, `http1-lines.wat`, and `http1-body.wat` validate smaller line/header/body primitives more strictly. | `not replacement`. WAT HTTP/1 modules are validators/scanners, not a full message parser replacement. Add a strict Rust parser policy before considering replacement. | A permissive full parser can normalize ambiguous requests differently from admission, cache, capability, or proof scanners. HTTP request proofs need the same accepted byte grammar at scan, parse, route, and hash time. | Add full-message strict tests for missing Host, malformed header without colon, invalid version such as `HTTP/x`, content-length longer than body, and relative target normalization. Add parity tests mapping each scanner acceptance to strict full-parser acceptance. |

## Default Use

Use strict WAT codecs for canonical validation, proof preimages, policy hashes,
package manifests, admission decisions, settlement evidence, and cache keys.
Use permissive Rust behavior only at explicitly named import, diagnostics, or
legacy compatibility boundaries. A WAT module with narrower scanner semantics is
not a replacement for a Rust parser until the table above has a replacement
policy and matching success/rejection tests.
