# เกี่ยวกับ Edgerun

Edgerun เริ่มจากความกังวลง่าย ๆ อย่างหนึ่ง: การสร้างซอฟต์แวร์บนชั้น abstraction ทึบ ๆ ซ้อนกันหลายชั้นกำลังกลายเป็นสิ่งที่ทำต่อไปได้ยาก เครื่องด้านล่างเร็วขึ้นเรื่อย ๆ แต่ระบบที่เราขอให้คนใช้งานกลับหนักขึ้น เปราะขึ้น และเข้าใจยากขึ้น.

ประโยคเก่าที่มักถูกอ้างว่า Bill Gates พูดว่า "640K ought to be enough for anybody" น่าจะไม่ใช่คำพูดจริง แต่ยังมีประโยชน์ในฐานะคำเตือน มันสะท้อนว่าซอฟต์แวร์ขยายตัวเร็วแค่ไหนเพื่อกินทรัพยากรฮาร์ดแวร์ที่มีอยู่ จากประสบการณ์ของผมเอง แค่ตั้งค่าแพลตฟอร์ม Kubernetes ก่อน deploy แอปจริงสักตัว ก็ใช้ RAM ประมาณ 12 GB แล้ว ซอร์สของ Chrome มีขนาดหลายสิบ GB ส่วน Android มีขนาดหลายร้อย GB และตอน build ก็เพิ่มอีกได้อีกหลายร้อย GB ตัวเลขพวกนี้กลายเป็นเรื่องปกติไปแล้ว แต่ไม่ควรรู้สึกว่ามันปกติ.

โลกเรามี compute มากมหาศาล สำหรับความต้องการปกติของคนทั่วไป เรามี CPU, memory, storage และ network มากเกินพอแล้ว ปัญหาคือแนวทางการสร้างซอฟต์แวร์สมัยใหม่ใช้ทรัพยากรพวกนั้นทิ้งไปจำนวนมากก่อนที่งานที่มีประโยชน์จะเริ่มด้วยซ้ำ ทุกชั้นที่เพิ่มเข้ามาขอ control plane, runtime, image format, cache, log stream, package graph, dashboard และ failure mode ของตัวเอง.

Edgerun คือการทดลองรับผิดชอบส่วนต่าง ๆ ของ stack ด้วยตัวเองมากขึ้น: identity, networking, storage, email, sites, code publishing และเครื่องมือปฏิบัติการรอบ ๆ สิ่งเหล่านี้ ไม่ใช่เพราะ abstraction ทุกอย่างแย่ แต่เพราะ abstraction ควรเล็กพอให้ตรวจสอบได้ ถูกพอให้รันได้ และซื่อตรงกับต้นทุนที่มันสร้าง.

เป้าหมายคือหาคำตอบว่าเราจะลดการพึ่งพา datacenter ขนาดใหญ่ที่ใช้พลังงานและสร้างมลพิษได้แค่ไหน โดยขยับไปสู่ระบบ peer-to-peer ที่มีประสิทธิภาพ และซอฟต์แวร์ที่รันใกล้กับคนที่ใช้งานมันมากขึ้น นั่นหมายถึงแพลตฟอร์มบังคับน้อยลง เครื่องที่ว่างเปล่าน้อยลง ความซับซ้อนที่ซ่อนอยู่น้อยลง และระบบที่คนคนเดียวหรือกลุ่มเล็ก ๆ เข้าใจได้มากขึ้น.

นี่เริ่มจากการทดลองจริง ไม่ใช่ manifesto ที่เสร็จสมบูรณ์ ในวิดีโอนี้ผมยังทดลองกับ Kubernetes สำหรับไอเดียนี้อยู่ ก่อนจะเริ่มตั้งคำถามจริงจังขึ้นว่า machinery พวกนั้นควรมีอยู่มากแค่ไหน:
