# Lifegraph v0 Conformance

## 1. Purpose

The conformance suite exists to prove that independent implementations of the Lifegraph v0 core protocol produce the same:

- canonical semantic bytes
- record hashes
- signatures
- validator outcomes
- state transitions where the protocol requires determinism

This suite is normative for protocol behavior, not for storage backend, runtime structure, transport implementation, or UI.

## 2. Scope

The v0 conformance suite covers the protocol families already fixed in the core spec:

- canonicalization and cryptographic input derivation
- stream append validation
- delegation chain validation
- command acceptance validation
- control transfer validation
- snapshot acceptance and delta application
- object retrieval and representation validation

The suite does **not** yet attempt to certify:

- relay economics
- market logic
- full network path selection heuristics
- daemon lifecycle
- local policy authoring UX
- storage proof markets
- remote compute safety models

## 3. Normative verdicts

Every validator MUST return one of these verdicts:

- `ACCEPT`
- `REJECT`
- `DEFER`
- `DUPLICATE`

Every non-accept outcome SHOULD also return a reason code from the common reason taxonomy.

### 3.1 Common reason taxonomy

Implementations MAY have additional internal reasons, but these external reasons are normative for cross-implementation comparison:

- `STRUCTURAL_INVALID`
- `CRYPTO_INVALID`
- `VERSION_UNSUPPORTED`
- `TARGET_MISMATCH`
- `REPLAY_DETECTED`
- `AUTHORITY_DENIED`
- `POLICY_DENIED`
- `MISSING_DEPENDENCY`
- `FORK_CONFLICT`
- `CANONICALIZATION_FAILED`
- `OBJECT_ID_MISMATCH`
- `SNAPSHOT_BASE_CONFLICT`
- `TIME_INVALID`
- `REVOCATION_ACTIVE`
- `ASSURANCE_INSUFFICIENT`
- `CONTROL_INVARIANT_FAILED`
- `REPRESENTATION_INVALID`

## 4. Harness model

A conforming harness MUST:

1. load a vector directory
2. load its declared semantic inputs and local state
3. run the designated validator or canonicalization routine
4. compare actual outputs to expected outputs
5. report pass/fail without adding implementation-specific reinterpretation

The harness MUST NOT pull unspecified network data, system time, or random values during a vector run unless the vector explicitly declares them.

## 5. Deterministic execution environment

For conformance runs, implementations MUST treat the vector as the complete source of truth for:

- current evaluation time
- local accepted stream heads
- locally trusted identities
- revocation knowledge
- assurance evidence
- payload objects
- representation bytes
- manifests and descriptors
- replay cache contents

If a validator would normally consult runtime stores, the harness must inject those stores from `local_state.yaml`.

## 6. Vector directory format

Each test case lives in its own directory.

Required files:

- `manifest.yaml`
- `semantic_input.yaml`
- `local_state.yaml`
- `expected.yaml`

Optional files:

- `canonical_signable.hex`
- `canonical_full.hex`
- `record_hash.hex`
- `signature_input.hex`
- `signature.hex`
- `canonical_bytes.hex`
- `representation_bytes.hex`
- `notes.md`

Derived artifacts are optional in the first draft corpus and may initially be generated by the reference implementation tooling rather than committed by hand.

## 7. Manifest format

`manifest.yaml` MUST contain:

- `id`: globally unique case id
- `suite`: one of `canonical`, `stream`, `delegation`, `command`, `control`, `snapshot`, `object`
- `validator`: exact validator or routine under test
- `version`: corpus version for the case
- `description`
- `priority`: `mandatory` or `optional`
- `tags`: array of descriptive tags

Example:

```yaml
{
  "id": "stream/01-genesis-valid",
  "suite": "stream",
  "validator": "validate_stream_append",
  "version": 1,
  "priority": "mandatory",
  "description": "valid node genesis event at seq 0",
  "tags": ["stream", "genesis", "accept"]
}
```

## 8. semantic_input.yaml

`semantic_input.yaml` contains the candidate object(s) under evaluation in semantic form.

Rules:

- use human-readable YAML structure
- use stable field names aligned to the abstract schema
- encode bytes as lowercase hex with `0x` prefix
- encode timestamps as RFC3339 UTC strings in the fixture layer
- represent enums by symbolic string names
- do not include derived hashes or signatures unless the vector explicitly tests full-form verification

This file is the semantic source the reference implementation canonicalizes.

## 9. local_state.yaml

`local_state.yaml` contains everything the validator needs besides the candidate input.

Possible sections:

- `now`
- `identity_store`
- `trust_roots`
- `revocations`
- `stream_heads`
- `stream_events`
- `replay_cache`
- `assurance_claims`
- `objects`
- `representations`
- `manifests`
- `snapshots`
- `policy_profile`

A validator MUST NOT assume missing local state means “fetch remotely”. Missing required dependency means `DEFER` or `REJECT` according to the core protocol rules.

## 10. expected.yaml

`expected.yaml` is normative.

It SHOULD include:

- `verdict`
- `reason_code` if not `ACCEPT`
- `derived` object, where applicable
- `post_state` object, where applicable

Examples of `derived`:

- `event_hash`
- `command_hash`
- `delegation_hash`
- `object_id`
- `representation_digest`
- `effective_capability_summary`
- `snapshot_acceptance_class`

Examples of `post_state`:

- new stream head
- replay cache entry
- resulting controller set
- acceptance class of a snapshot
- object validation level

## 11. Comparison rules

### 11.1 Canonicalization vectors

A canonicalization vector passes only if the implementation produces byte-for-byte identical canonical bytes to the committed expected bytes.

### 11.2 Hash/signature vectors

A hash/signature vector passes only if:

- canonical bytes match expected canonical bytes
- record hash matches expected hash
- signature input matches expected signature input
- signature matches expected signature (when the vector includes a private test key)

### 11.3 Validator vectors

A validator vector passes only if:

- verdict matches
- reason code matches when verdict is not `ACCEPT`
- required derived fields match exactly
- required post-state fields match exactly

Implementations MAY emit additional internal diagnostics, but they do not count toward conformance.

## 12. Key fixtures

Test vectors SHOULD reference deterministic fixture keys by fixture id.

Recommended fixture ids for v0.1:

- `user_alice`
- `user_bob`
- `node_phone`
- `node_server`
- `agent_assistant`

The first draft corpus may reference these fixture ids without embedding private keys in the repository. The reference implementation may load the private test keys from a separate fixture file or environment reserved for test execution.

## 13. Corpus evolution

Each vector case has its own `version`. If a case is materially changed, increment the case version.

Corpus-wide release tags SHOULD be maintained, for example:

- `vectors-v0.1`
- `vectors-v0.2`

A released vector corpus MUST be immutable.

## 14. CI gate

A build claiming conformance to Lifegraph v0 MUST pass all `mandatory` vectors for the targeted corpus release.

Optional vectors are strongly recommended and should become mandatory only when the protocol section they test is considered fully frozen in practice.

## 15. Initial mandatory set

The initial draft corpus contains 25 mandatory cases:

- 5 canonical
- 4 stream
- 4 delegation
- 4 command
- 3 control
- 3 snapshot
- 2 object

This is enough to catch almost all protocol drift in early implementations.

## 16. Output format from harness

The harness SHOULD emit machine-readable results:

```yaml
{
  "case_id": "command/01-commit-success",
  "passed": true,
  "verdict": "ACCEPT",
  "reason_code": null,
  "derived": {
    "command_hash": "0x..."
  }
}
```

and a human summary for CI:

```text
PASS command/01-commit-success
FAIL snapshot/03-delta-gap-defer expected DEFER got REJECT
```

## 17. First implementation rule

Before any implementation claims protocol compatibility, it SHOULD pass:

- all canonical vectors
- all stream vectors
- all delegation vectors
- all command vectors

Those four groups define the semantic core.
